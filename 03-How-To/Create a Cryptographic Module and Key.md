# Create a Cryptographic Module and Key

**Goal:** have a named module in the Key Management Framework with an algorithm, an active key generated by the instance, and a policy saying who may use it.
**Prerequisites:** `admin` and `security_admin` to appoint the first KMF admin; then `sn_kmf.cryptographic_manager` for the rest.
**Navigation:** All > Key Management > Cryptographic Modules

Background: [[Key Management Framework (KMF)]], [[Module Access Policies (MAPs)]].

## Steps

1. **Roles.** Elevate to `security_admin`. **System Security > Key Management Administration**: move the user to the selected side, **Save** (they get `sn_kmf.admin`). As that user, add `sn_kmf.cryptographic_manager` on the user records that need it.
2. **Key source.** **System Security > Field Encryption Settings**: **Key Source** = *ServiceNow Generated Keys*, **Save**.
3. **Module.** **Cryptographic Modules > Create New**: **Module name**, **Crypto spec template** = *Default*, **Default module access policy value**, life-cycle state *Draft*. **Submit**. The name is stored with the scope in front.
4. **Specification.** Open the module > *Crypto Specifications* tab > **New**: **Crypto purpose**, **Algorithm**, **Operation mode**, **Size**, optionally **Equality preserving**. **Next**.
5. **Life cycle** (optional). Pick a row in the *Key Lifecycle* table to set, for example, an expiry relative to activation. **Next**.
6. **Key.** **Origin** = *ServiceNow*, a **Key alias**, **Next**, **Generate Key**. The first key is active; see it on the *Module Keys* tab.
7. **Publish** the module (life-cycle state *Published*).
8. **Access.** **Key Management > Module Access Policies > All > New**: name, the module, **Type** = Role with the **Target Role**, **Result** = Track, **Active**. **Submit**.

## Result / how to check it worked

The module's page shows the specification, one *Active* key, and the user under *Users with access*. To see a decision being made, switch on **Diagnostics > Session Debug > Debug Module Access Policies** and open a page that uses the module.

To replace the key later: *Module Keys* > the active key > **Rotate Key**. The old key becomes *Deactivated* and still decrypts.

## Example

Module `example_hr_notes` created in the global scope (stored as `global.example_hr_notes`). Specification: *Symmetric Data Encryption/Decryption*, AES, CBC, 256 bit. Life-cycle rule: expiry one year after activation. Key alias `example_hr_notes_key_1`, generated by the instance. Access policy *Example HR readers*: type Role, target role `u_example_hr_reader`, result Track. *Test User*, who has that role, appears under *Users with access*.

## Tables / fields involved

- `sys_kmf_crypto_module` (module), `sys_kmf_module_key` (keys), `sys_kmf_crypto_caller_policy` (access policies)
- Property `com.glide.encryption.cle_kmf.key_source`

## Gotchas

- A module **cannot be deleted**: name it carefully.
- Without Field Encryption Enterprise: five published modules, five access policies, role-type policies only, no customer-supplied keys.
- No access policy means nobody can decrypt: fields protected by the module look empty.
- Never destroy a key whose data still matters; destroyed means unreadable for good.
- Key actions work on custom modules only, not on base system modules.
- A clone does not carry keys: see [[KMF Key Exchange and Key Import]].
