# Key Management Framework (KMF)

**In one line:** KMF is the part of the platform that creates, stores, rotates and controls access to cryptographic keys; everything that encrypts or signs on an instance (field encryption, Password2 fields, code signing, secrets) is a **cryptographic module** inside it.

From the Brazil docs. Follows NIST 800-57. In the base system; no domain separation support; works on self-hosted instances. Who may use a module: [[Module Access Policies (MAPs)]]. Moving keys between instances: [[KMF Key Exchange and Key Import]]. Steps: [[Create a Cryptographic Module and Key]].

## Building blocks

| Component | What it is | Where |
|---|---|---|
| **Cryptographic module** (`sys_kmf_crypto_module`) | the parent record for one use case: which mechanism, which keys, who may use them. Cannot be deleted | **All > Key Management > Cryptographic Modules > All** |
| **Cryptographic specification** | purpose, algorithm, key size and key origin of a module | *Crypto Specifications* tab of the module |
| **Module key** (`sys_kmf_module_key`) | the key itself, generated by the instance or supplied by the customer | *Module Keys* tab |
| **Module access policy** | who or what may encrypt and decrypt with the module | *View access policies* link; [[Module Access Policies (MAPs)]] |
| **Life-cycle policy** and **module policy exception** | limits such as how long a key lives | **Key Management > Lifecycle Policies > Instance Policies**; *Module Policy Exceptions* tab |

Module form: **Module name** (referenced by scripts; saved with the scope in front, as in `global.my_crypto_module`), **Crypto spec template** (*Default*), **Default module access policy value** (rely on system default, Reject, Track), **Crypto module life-cycle state** (Draft while configuring, Published to use).

## Purposes and algorithms

| Crypto purpose | Algorithm | Key sizes |
|---|---|---|
| Asymmetric data encryption / decryption, asymmetric key wrapping / unwrapping, signature generation / verification | RSA | 2048, 3072, 4096 bit |
| Symmetric authenticity | HMAC | 256, 384, 512 bit |
| Symmetric data encryption/decryption, symmetric key wrapping/unwrapping | AES in CBC, CFB, OFB, CTR or GCM mode | 128, 192, 256 bit |

- AES-CBC offers the **Equality preserving** option (the same clear text always gives the same cipher text, so equality filters work); Field Encryption Enterprise uses AES-CBC. The field help on the specification form describes the option the other way round (as enabling non-deterministic encryption): the overview table and the option's name agree on deterministic.
- AES-GCM has built-in integrity.

## Key hierarchy (envelope encryption)

Each key is encrypted ("wrapped") by the one above it; the top lives in a hardware security module rated FIPS 140-2 level 3 (SafeNet KeySecure).

| Key | Kept in | Role |
|---|---|---|
| Root Key (RK) | HSM | unwraps the IRK |
| Instance Root Key (IRK) | HSM | unique per instance; wraps the instance's internal keys |
| Instance Key Encryption Key (IKEK) | instance, wrapped | wraps the module keys |
| Instance HMAC Key (IHK) | instance, wrapped | integrity and authenticity of module keys |
| Instance Asymmetric Encryption Key (IAEK) | instance | confidential messages between instances (key exchange, Instance Data Replication approval) |
| Instance Signature Key (ISK) | instance | signing |
| Password2 key | instance | Password2 fields ([[Password2 Fields and the GlideEncrypter Deprecation]]) |
| Customer Data Encryption Key (CDEK) | instance | keys created through KMF, wrapped by the IKEK |
| IDR Data Encryption Key | instance | Instance Data Replication |

Self-hosted and developer instances use a *File Key Store* in place of KeySecure.

## Key life cycle

| State | Meaning |
|---|---|
| Generated | created; the first key generated becomes active automatically |
| **Active** | used for new encryption or signing. **One active key per specification** |
| Suspended | unusable until resumed (only if no other key is active) |
| Deactivated | no new content, still decrypts and verifies. Rotation leaves the old key here |
| Revoked, Compromised | as deactivated, with the reason recorded |
| Destroyed | key material removed for good: **data encrypted with it is lost** |

| Action | Effect |
|---|---|
| **Generate Key** | new key; active if it is the first |
| **Rotate Key** | deactivates the active key and activates a new or imported one; key version +1 |
| **Revoke Key** | marks the key revoked (reason required); a new key is generated for new data |
| **Suspend Key** / **Resume Key** | take the active key out of use and back |
| **Renew** | postpones the expiry by the original lifetime; needs an expiration date in the life-cycle definition and a key in Active or Renewed |

- Actions are on the key record (*Module Keys* tab > key alias), which also shows the generation, activation, rotation, deactivation, destruction and expiry dates, past and planned.
- Only for custom modules, not base system modules.
- Contradiction: the actions page says a key cannot be destroyed; the states page says deactivated keys can be destroyed by life-cycle automation after a configured period of non-use.
- Encryption modules (unlike the older encryption contexts) support a rekey: re-encrypting existing records with the new key.

## Life-cycle rules, three levels

1. **Instance policies** (**Lifecycle Policies > Instance Policies**): boundaries for the whole instance, as a **Policy condition** with **Result** Reject or Track. Example: expiry never more than two years after activation.
2. **Life-cycle templates**: default rules per key type.
3. **Life-cycle rules** on a specification (*Lifecycle Definition* step): **Applies to**, **For field**, **Type** (Relative or Absolute), **Relative duration type** (years, months, days), **Relative duration**, **Relative operation** (before, after), **Relative to**, **Order**.

A **module policy exception** (roles `sn_kmf.cryptographic_manager` and `sn_kmf.admin`) relaxes or tightens the instance policy for one module and one key type.

## Roles

| Role | Does |
|---|---|
| `sn_kmf.admin` | assigns the other KMF roles; everything the manager can do. Holder must also have `admin` and `security_admin`. Also needed to edit any group that carries `sn_kmf.cryptographic_manager` |
| `sn_kmf.cryptographic_manager` | create and update modules and access policies; generate, rotate, revoke keys; life-cycle operations |
| `sn_kmf.cryptographic_operator` | renewal, rotation, revocation only |
| `sn_kmf.cryptographic_auditor` | read modules, key metadata, life-cycle details and access policies |
| `sn_kmf.cryptographic_integrator` | integrate KMF with external keystores |

- Without a KMF role the lists and modules are not reachable at all.
- First KMF admin: elevate to `security_admin`, **System Security > Key Management Administration**, move the user to the selected side, **Save**. That user then grants the other roles on user records.

## Key source

**System Security > Field Encryption Settings > Key Source** (property `com.glide.encryption.cle_kmf.key_source`): *ServiceNow Generated Keys* or *Customer Supplied Keys*. Customer-supplied keys need Field Encryption Enterprise.

## Health

**Key Management > Diagnostics**: one line per component with Operational (green), Disabled (grey), Degraded (yellow) or Malfunction (red); checked every 15 seconds.

Components: Key Secure, File Key Store, GlideEncrypter module, IKEK, Instance HMAC Key, Vault PKI, EJBCA PKI, Instance PKI (ServiceNow data centres only). A parent is degraded if any subcomponent is degraded or failed, failed if all are.

## Licensing

- KMF and Field Encryption with encryption modules are in the base system (non-enterprise Field Encryption is limited to **five** published modules and five access policies).
- **Platform Encryption** bundle (`com.glide.now.platform.encryption`): Field Encryption Enterprise (unlimited) and Cloud Encryption. The landing page also lists Database Encryption in the bundle.
