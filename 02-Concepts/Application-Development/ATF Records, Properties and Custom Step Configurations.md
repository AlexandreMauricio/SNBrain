# ATF Records, Properties and Custom Step Configurations

**What it is:** the reference part of the ATF docs: what is not rolled back, the result records and their statuses, design rules, the property list, how a scripted step configuration is written, the component actions available in Configurable Workspace tests, and the docs' worked examples.

From the Brazil docs. Concepts and roles: [[Automated Test Framework Overview]]. Building: [[ATF Building and Running Tests]]. Suites and administration tasks: [[ATF Test Suites, Schedules and Administration]]. Steps: [[ATF Test Step Categories Reference]].

## Not rolled back

ATF tracks what a test inserts, updates or deletes and undoes it afterwards, **except** on these tables (and anything extending them):

| Excluded | |
|---|---|
| Named tables | History (`sys_history_line`), ECC Queue (`ecc_queue`), Email (`sys_email`), Email Log (`sys_email_log`), `report_executions`, `report_stats`, `sys_execution_tracker`, `sys_progress_worker`, `sys_schema_change`, `sys_upgrade_history`, `sys_upgrade_history_log`, `sys_mutex`, `sys_plugin_log`, `sys_status`, `sys_number_counter`, `sys_amb_channel_presence` |
| Name prefixes | `syslog`, `sys_amb_message`, `sys_cluster`, `cmdb_metric`, `ts_`, `v_`, `sys_delete_recovery` |

Consequences: emails generated by a test stay in `sys_email`, and **numbers consumed by test records are not given back** (`sys_number_counter`).

## Design rules

- Tests create their own users (*Create a User*) and records; never impersonate, validate against, modify or delete existing ones.
- Do not touch system tables or tables extending Application File (`sys_metadata`): disabling a business rule or changing a property changes behaviour for every other test running in parallel. The docs' summary writes the table as `sysmetadata`; `sys_metadata` is the name.
- Tests that cannot avoid a shared resource are marked mutually exclusive.
- Custom UI steps: only your own pages (not dashboards or platform designers); component lists are retrieved again on each instance.
- Server UI actions: choose an assert type other than *None* and set a timeout (for server UI actions *None* is treated as *Form submitted to server*).
- Domain separation: set the domain in the **first impersonation step**.
- Clone production over sub-production to get current tests; run tests only on non-production.

The test form shows a warning for each of these (impersonating an existing user, using a `sys_metadata` or system table, using or modifying an existing record, assert type *None*).

## Records

Table names are given only where the docs name them.

| Record | Fields worth knowing |
|---|---|
| Test | **Name**, **Description**, **Active**, **Application**, **Fail on server error** (errors on the server during UI steps fail the test); actions **Run test**, **Copy test** |
| Test suite | **Name**, **Active**, **Description**, **Application**, **Parent Suite**; lists *Test Suite Tests*, *Child Test Suites*, *Test Suite Results*, *Test Suite Schedules* |
| Test result (`sys_atf_test_result`) | **Status**, **Retain indefinitely**, start, end, **Duration**, **Previous test result** (only on a re-run), **Output**, **Browsers involved** (user agents). Section *Client Error Details* (failing step, summary, first failing client error, screenshot) or *Failure Details* (failing step, summary, screenshot). Lists *Step Results*, *Test Log*, *Test Transactions* (`syslog_transaction`), *Warnings* |
| Step result (`sys_atf_test_result_step`) | **Status**, **Summary**, **Output** (for a REST step the request and response, **truncated at 4,096 characters**, filtered headers shown as "Header redacted for security"), **Step**, **Description**, times; list *Step Transactions* |
| Test log (`sys_atf_test_result_item`) | **Type**: Step Result, Client Log, Client Error; **Output**; **Recorded at**; **Allow listed client error** |
| Suite result (`sys_atf_test_suite_result`) | **Number**, **Base Test Suite Result** (top of the hierarchy), **Parent**, **Status**, **Run time**, **Retain indefinitely**, rolled-up counts of successes, failures, errors and skips (this suite plus all descendants); lists *Test Results*, *Child Test Suites Results*, *All Test Suite Results*, *Failed Tests in Suite* |
| Suite schedule | **Run** (frequency), **Run as tz**, **Time**, **Day**, **Repeat interval** (for Periodically), **Conditional** + **Condition** script |
| Scheduled suite run | **Schedule**, **Test Suite**, **Watch list**, **Browser name**, **Browser version starts with**, **OS name**, **OS version starts with** (no matching runner = the suite does not run). To find the exact strings, start a scheduled runner in that browser and read its record |
| Test runner | **Type** (Manual, Scheduled), **User**, browser and OS name and version, **Status** (Online, Offline), **Last checkin**, **Status reason**. A runner's preferences panel has **Screenshots mode** and **Run scheduled tests only** (switches it between manual and scheduled) |
| Allowed client error (`sys_atf_whitelist`) | **Report level**, **Active**, **Error message**, **Description**. Module *Reported Client Errors* lists failed client-error logs across all tests |

### Statuses

| Status | Meaning | On |
|---|---|---|
| Success | passed | all |
| Failure | failed | all |
| Success with warning(s) | passed, with a client error allowed at level Warning | all |
| Warning; Ignored | a client error allowed at that level | logs, suite results |
| Waiting; Running | | tests, suites, logs |
| Skipped | an earlier test of the suite failed with **Abort on failure** | all |
| Error | the framework itself failed (runner stopped, server problem); message in the step result **Summary** | all |
| Cancelled | cancelled by a user | all |

Results are deleted after 30 days unless **Retain indefinitely** is ticked ([[Table Cleaner]]; the *Autoflush* form: **Tablename**, **Matchfield**, **Age in seconds**, **Cascade delete**, **Conditions**).

## Custom step configurations

A **step configuration** defines a step type. **Administration > Step Configurations**. Base ones are read-only; custom ones are always **Class type** *Script* and can only use the **Server - Independent** step environment (custom environments cannot be added).

| Field | Meaning |
|---|---|
| **Name**, **Active**, **Application** | |
| **Step Environment**, **Category** | where it runs; where it is listed in *Add Test Step* |
| **Batch order constraint** | *None*; *Start Batch Execution* (must be first); *Run in the middle of an execution* (neither first nor last); *Stop Execution* (must be last) |
| **Order** | position in the step list |
| **Template reminder** | instruction written into the test description when the step arrives through a template |
| **HTML description** | text shown when the step is highlighted in the dialog |
| **Description generation script** | builds the step's description from its inputs |
| **Step execution script** | what the step does |
| *Input Variables*, *Output Variables* lists | typed variables: **Type**, **Label**, **Column name** (the name used in script), **Max length** |

Step execution script (server side, in the step configuration's application scope):

```js
(function executeStep(inputs, outputs, stepResult, timeout) {
  if (gs.nil(inputs.table)) {
    stepResult.setOutputMessage('The table input was not specified');
    stepResult.setFailed();
    return;
  }
  var gr = new GlideRecord(inputs.table);
  gr.addEncodedQuery(inputs.field_values);
  gr.query();
  if (!gr.next()) {
    stepResult.setOutputMessage('No records matching ' + inputs.field_values);
    stepResult.setFailed();
    return;
  }
  outputs.table = inputs.table;
  outputs.first_record = gr.getUniqueValue();
  stepResult.setOutputMessage('Found ' + gr.getRowCount() + ' records');  // last call wins
  stepResult.setSuccess();
}(inputs, outputs, stepResult, timeout));
```

- Waiting for asynchronous work: loop up to `timeout`, calling `sn_atf.AutomatedTestingFramework.waitOneSecond()` between checks. The same loop works in *Run Server Side Script*, with `return true` / `return false` instead of `setSuccess()` / `setFailed()`.
- Description generation script: `(function generateDescription(step) { ... return text; })(step);` with inputs as `step.inputs.<name>`; the docs' sample uses `ATFStepDescriptionGenerator().getConditionDescription(table, conditions)`.
- **More outputs for *Run Server Side Script*:** open its (read-only) step configuration, add a row to *Output Variables*, then set `outputs.<column_name>` in the test script.
- **More outputs for *Custom Scripted StepConfig*:** **Copy** it first (the copy is editable), then add outputs and change the script.

## The docs' worked examples

| Goal | Steps |
|---|---|
| Basic form | Impersonate > Open a New Form (Catalog Task) > Set Field Values (including mandatory ones) > Submit a Form |
| Use an earlier output | Record Insert (incident) > Open an Existing Record with **Record** mapped to step 1's output > Field Values Validation |
| Business rule | Impersonate > Open a New Form (User) > Set Field Values (**Active** false) > Submit > Field Values Validation (**Locked out** is true) |
| Data policy | Impersonate > Open a New Form (incident) > Field State Validation (**Assignment group** not mandatory) > Set Field Values (**Impact** High) > Field State Validation (mandatory) |
| Script include | Run Server Side Script calling it and comparing the return value; or a form step that triggers it, then Field Values Validation, Field State Validation or Record Query |
| Catalog fulfilment | Replay Request Item > for each approver: Impersonate, Record Query for the approval (`first_record`), Record Update to Approved > for each catalog task: Record Query, Record Update to Closed Complete > Record Validation on the requested item and on the request |
| REST | Record Insert (incident) > Send REST Request - Inbound - REST API Explorer (namespace `now`, Table API, `incident`), then set a basic authentication profile and map the inserted record into **Path** > Assert Status Code is 200 > Assert Response JSON Payload is Valid > Assert JSON Response Payload Element. Role `atf_ws_designer` |

## Discrepancies in the docs

- *Waiting/running test runs* says only one test runs at a time and a test queued for more than ten minutes is cancelled; the parallel testing pages describe several tests running at once. Probably an older page (?).
- The catalog example says that in Brazil "you cannot create an automated test for the process by which the user creates a new request", yet the Service Catalog step categories do exactly that. It also writes the requested item table as `sc_request_item`; the table is `sc_req_item`.
- In the component tables the descriptions of **Date-Time-Interval** and **now-alert-list** are shifted against the action names (for example *Dismiss alerts* described as checking for an action button). The action names above are from the first column only.
- The roles page labels `atf_ws_designer` "ATF workspace designer" although it is about web service (REST) authentication.
- Defaults marked `?` are not given on the properties page.
