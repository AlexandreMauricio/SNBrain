# Flow Administration, Execution Details and Access

**What it is:** how to see what flows did, how long that evidence is kept, how to tune priority, and who may build, view or call flows. Concepts: [[Flows, Subflows and Actions Overview and Architecture]].

## Admin modules (Process Automation > Flow Administration)

| Module | Shows |
|---|---|
| Today's Executions | flow contexts run today |
| Active flows | contexts in state Waiting |
| Event Queue | events with queue `flow_engine` and state Ready: flows waiting to be processed |
| Operations Dashboard | counts and average runtime, today or 30 days |
| FDIH Dashboard (admin) | reporting state and log level, flow usage by state and period, Integration Hub usage, flow executions (filter by calling source), MID executions, and a Debug list of flow jobs waiting to run |
| Settings | execution setting records |
| Properties | flow system properties |
| Feature Access List, Content Definitions, Content Filtering Rules | access control below |
| Complex Object Templates, Usage Overview | Integration Hub |

## Execution details

Opened from the Operations tab or a flow's **Executions**. Header: flow name, refresh, state, links (**Open Flow**, **Open Context Record**, **Open Flow Logs**, **Open Current Record**, **Open Action**). Per component: calling source, run as, run with roles, configuration details (inputs with their pills and runtime values), output data, logs (UTC), steps (custom actions only), start time, run duration (ms; since Washington DC it includes time in the event and ECC queues and with the MID Server), retry info, integration metadata. Loops offer a selector per iteration. Long text opens in an embedded viewer.

| Execution state | Meaning |
|---|---|
| Completed | all actions ran |
| Cancelled | manually, or the run exceeded the timeout |
| Waiting | paused on a condition; **Cancel Flow** available |
| Paused | yielded to higher-priority flows or a node shutdown |
| Presumed Interrupted | running over 15 minutes with no valid transaction on its node, or over 8 hours on another node |
| Error | stopped at the failing action; **Go to error** |

Calling sources: Workflow Studio Test, CRUD Trigger, Date Trigger, Metric Trigger, Service Catalog Trigger, Script, Background Script.

### Reporting level

| Level | Generates |
|---|---|
| Off (default) | nothing, except when testing (tests always report at Trace) |
| Basic | state and duration of each flow, subflow and action; trigger and subflow input / output values |
| Full (debugging) | plus input and output values of every action, and of the steps of custom actions |
| Trace (testing, Support) | everything including steps |

Set for everything with property `com.snc.process_flow.reporting.level` (*Level of reporting data generated by the flow engine*), or per item: open it > **More actions** > reporting settings (roles `flow_operator` or admin). Runs made while reporting was off never get details later. Avoid Full on production. Values in Full and Trace are visible only with `fd_read_operations_all`; a flow that ran with privileged roles (or as System) shows its details only to users holding those roles. Property `com.snc.process_flow.reporting.serialized.val_size_limit` truncates stored values.

### Execution settings (`sys_flow_execution_setting`)

One record per flow, subflow or action, overriding the global level: **Flow/SubFlow/Action**, **Report all iterations** (otherwise only the first and last loop iterations), **Reporting**, **Logging** (threshold for writing to the flow log), **Flow Priority** (hidden: add it to the list and form layout). Children run under the parent flow's settings. Delete the record when troubleshooting is over.

## Retention (table cleaner)

| Table | Holds | Kept |
|---|---|---|
| `sys_flow_context` | context and process plan of every run. No custom business rules on this table | 2 weeks if complete; 6 weeks if error or cancelled. Lengthening it hurts performance |
| `sys_flow_context_chunk` | runtime data of running flows. Never edit | until the flow stops |
| `sys_flow_context_chunk_archive` | the same for stopped flows | with the context |
| `sys_flow_report_doc`, `_chunk`, `_chunk_archive` | execution detail reports | with the context |
| `sys_flow_log` | copies of log entries tied to a context | 28 days (table rotation) or with the context |
| `sys_flow_plan_context_binding` | the unique key per trigger and record behind *Run once* and *unique change* | 12 months. After removal a "once" flow can run again for the same record |
| `sys_json_chunk` | plans of flows created before San Diego. Never edit | with the parent |

Lost details can only come back from an instance backup through Support. See [[Table Cleaner]], [[Database Rotation - Table Rotation and Table Extension]].

## Priority

Only for background flows. High, Medium (default) or Low: flow **Properties > Advanced Options > Flow Priority Default** (role `flow_designer`), or the execution setting.

- Workflow Studio may use up to half the worker threads. Workers take several higher-priority flows before a lower one.
- A flow queued over one minute is delegated to another node and loses its priority; so does any flow that pauses (it resumes at Medium).
- A low-priority flow running over two minutes is paused when no high-priority flow ran in the last five minutes and at least 100 are queued (property `com.glide.hub.pause_low_priority_flows_enabled`).
- High: rare, short, business-critical flows. Low: high-volume, not time-sensitive. Leave flows that wait at Medium. Not everything High.

## Roles

| Role | Can | Contains |
|---|---|---|
| `flow_admin` | limited admin over all flow content | `flow_designer`, `flow_operator`, `action_designer`, `action_category_creator`, `flow_designer_scripting`, `connection_admin`, `flow_report_viewer`, write-enabled roles |
| `flow_designer` | build flows and subflows. **Effectively admin**, because flows can run as System | `flow_operator`, `trigger_designer` |
| `action_designer` | build actions, in any scope | |
| `flow_designer_scripting` | write inline scripts in inputs | |
| `flow_operator` | view executions, dashboards, logs | |
| `trigger_designer` | saved triggers | |
| `action_category_creator` | action categories | |
| `flow_report_viewer` | reports on flow tables | |
| `fd_read` | open designers read-only | `fd_read_flows`, `fd_read_actions`, `fd_read_operations` |
| `fd_read_operations` / `fd_read_operations_all` | basic / all generated execution details | |

Do not combine read-only roles with write roles. Delegated development is the safer way to give authoring rights inside one application. Application UI actions such as *Flow Context* on a requested item need that application's role (for example `itil`).

**See related flows** (More Actions on an action or subflow): which flows use it and whether they are active, before changing inputs.

### Feature access and content filtering

- **Feature Access List**: per UI feature (Save, Test, Activate, Copy, Code snippet, Stages, Error Handler, Executions, Properties, Manage security, Diagramming View ...) list the roles required, always including `flow_designer`; then tick **Enable feature access filtering?**. Without the role the feature does not render.
- **Content definitions** (a table such as Flow `sys_hub_flow`, conditions, resource tags) plus **content filtering rules** (one role ↔ one definition) hide triggers, actions, subflows, flow logic or steps from authors. A flow containing something the user cannot access is **read-only** for them and cannot be copied (transform functions are the exception: only the function is read-only).

## Calling flows from script

| API | Where | Notes |
|---|---|---|
| `sn_fd.FlowAPI` | server-side | run a flow, subflow or action synchronously or asynchronously. *Quick* methods (`executeFlowQuick`, `executeSubflowQuick`, `executeActionQuick`, `startFlowQuick`, `startSubflowQuick`, `startActionQuick`) create no context or details, keep the flow's priority, and always run as System |
| `GlideFlow` | client-side | only for items marked client callable |
| JSON / XML streaming builders | server-side | build large payloads for REST or SOAP steps |

The guide names the class only as FlowAPI; the `sn_fd` namespace is general knowledge. Flows and subflows run as System or as the initiating user (flow property); actions run as the initiating user.

- **Create Code Snippet** (More Actions; active flow or published action): a ready JavaScript call to paste into a business rule or Scripts - Background.
- **Client callable** (role `security_admin`): create an ACL of type `client_callable_flow_object`, operation execute, with a role; then on the item **Manage security > Callable by Client API** and add that ACL. Consider what data it exposes.

## Cross-scope access

Restricted Caller Access records have source types **Flow** (core actions: approval covers that operation on that resource for the whole flow, per flow) and **Flow Action** (custom actions: approved once, valid wherever the action is used). Instances upgraded from San Diego or earlier need property `com.glide.hub.flow.restricted_caller_access.track_flows_as_source` = true; afterwards cross-scope flows are blocked until their requests are set to Allowed, so plan it.
